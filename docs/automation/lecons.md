# Journal des leçons — vers un standard de sous-projet et des skills Claude Code

Ce fichier alimente deux livrables de fin de phase : `docs/automation/standard-sous-projet.md`
et la liste des skills à créer. Il est complété **à la fin de chaque lot**.

Quatre natures, systématiquement distinguées :

| Marque               | Sens                                                                         |
| -------------------- | ---------------------------------------------------------------------------- |
| 🟦 **générique**     | Va dans le standard, réutilisable dans tout sous-projet                      |
| 🟨 **ns-studio**     | Propre à ce dépôt, ne pas généraliser                                        |
| 🟥 **friction**      | La boucle de travail a coincé : étape floue, attente, vérification manquante |
| ⚙️ **à automatiser** | Devrait devenir un hook, une étape CI ou un script                           |

## Lot 0 — Assurer le retour arrière

### 🟦 Générique — à verser au standard

| Leçon                                                                                                                                                              | Pourquoi                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Une sauvegarde de prod Workers = identifiant de version Cloudflare + archive des fichiers ; l'un sans l'autre est incomplet.**                                   | L'archive ne couvre que les assets statiques : elle ne contient ni le code du Worker, ni sa configuration, ni ses bindings. Seul `wrangler rollback <id>` restaure l'ensemble. Inversement, un identifiant seul dépend de la rétention Cloudflare. **Les deux moitiés, relevées avant tout déploiement.** → checklist « sous-projet conforme ». |
| **Une sauvegarde non vérifiée n'est pas une sauvegarde.** Comparer l'archive à la production **fichier par fichier, par empreinte**, avant de la déclarer valable. | Ici c'était vrai (8/8 identiques), mais rien ne le garantissait : le `dist/` est ignoré par Git et pouvait avoir dérivé.                                                                                                                                                                                                                        |
| **Ne jamais combler une donnée de production manquante par une valeur plausible.** Laisser le champ vide et nommer le blocage.                                     | Un identifiant de version inventé produit un `wrangler rollback` qui échoue précisément au moment où on en a besoin — un faux filet est pire que pas de filet.                                                                                                                                                                                  |
| **Les artefacts de sécurité ne vont jamais dans `/tmp`** — vidé au redémarrage. Destination : `~/backups/<projet>-<objet>-<date>/`.                                | Une photo d'avant perdue rend le critère de non-régression invérifiable.                                                                                                                                                                                                                                                                        |
| **La photo d'avant doit inclure le fichier entier, pas seulement un résumé.** Copier `package-lock.json`, pas juste la liste des versions.                         | Le mode `--compare` a besoin de la source complète (`version`, `resolved`, `integrity`).                                                                                                                                                                                                                                                        |
| **Vérifier l'accès aux outils distants au tout début d'une phase**, pas au moment où on en a besoin.                                                               | Le jeton OAuth wrangler avait expiré 35 jours plus tôt : découvert à la première commande.                                                                                                                                                                                                                                                      |
| **Avant d'épingler un outil, vérifier que son `engines` accepte le runtime épinglé du projet.**                                                                    | `npm@12.2.0` → `engines.node = ^22.22.2 \|\| ^24.15.0 \|\| >=26.0.0`, qui accepte bien Node 22.23.2.                                                                                                                                                                                                                                            |

### 🟥 Frictions rencontrées

| Friction                                                             | Détail                                                                                                                                                                                                     | Remède                                                                                                                                                                                   |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Faux négatif d'empreinte sur les redirections**                    | `curl` sans `-L` sur `/index.html` renvoie un corps vide (307 → `/`) ; `sha256` = `e3b0c442…`, celle de la chaîne vide. Deux fichiers sur huit sont apparus « DIFFERENT » à tort.                          | Toute comparaison d'empreinte HTTP doit utiliser `-L` **et** rejeter explicitement l'empreinte de la chaîne vide. ⚙️ à intégrer au script de vérification.                               |
| **Authentification expirée, non rafraîchissable sans interactivité** | Wrangler refuse de rafraîchir un jeton OAuth dans un shell non interactif, même avec `refresh_token` + `offline_access` présents.                                                                          | L'agent **ne doit pas** s'authentifier à la place de l'utilisateur. Le skill doit détecter ce cas, l'annoncer, fournir la commande exacte, et **continuer tout ce qui n'en dépend pas**. |
| **Archéologie manuelle de la cause racine**                          | Trouver _pourquoi_ le lock était cassé a demandé `git log --follow` par version du lock, puis la lecture de 7 logs CI. Deux causes racines distinctes, dont une invisible dans le rapport d'audit initial. | ⚙️ Un skill `diagnostic-ci` devrait automatiser : échecs CI → première occurrence → bissection du fichier fautif.                                                                        |

### ⚙️ À automatiser

- Script de comparaison **archive ↔ production** (suit les redirections, rejette l'empreinte vide).
- Vérification d'accès aux services distants (`gh auth status`, validité du jeton wrangler) en **préambule de phase**.
- `gh secret list` dans la checklist « sous-projet conforme » : ici, l'absence de `CLOUDFLARE_API_TOKEN` a coûté 2 échecs CI avant même le problème de lockfile.

### 🟨 Propre à ns-studio

- Le `dist/` **non versionné était la seule copie de la production** — situation à supprimer en Phase 1 (artefact de build attaché à la release).
- macOS 12.6 interdit workerd : pas de `wrangler dev`, donc toute vérification de runtime est repoussée après déploiement.

## Lot 1 — Lockfile multi-plateforme et npm unique

> _Clos le 2026-11-02 — PR [#1](https://github.com/nseng-dev/ns-studio/pull/1) fusionnée, CI verte._

### 🟦 Générique — acquis pendant l'enquête

| Leçon                                                                                                                                   | Pourquoi                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **« Même outil, même version, en local et en CI. »** Épingler npm explicitement, jamais celui qu'embarque Node.                         | Node 22.23.2 embarque npm 10.9.8, antérieur au correctif de npm/cli#4828 (npm ≥ 11.3.0). Suivre « `nvm use` puis `npm install` » aurait reproduit le bug.        |
| **Un lockfile se vérifie, il ne se suppose pas.** Invariant : toute `optionalDependencies` déclarée doit avoir son entrée dans le lock. | Garde validée empiriquement : lock sain `22edb63` → 202 déclarées / **0 absente** ; lock cassé → 193 déclarées / **172 absentes**. Zéro faux positif.            |
| **Réparer un lock ≠ le régénérer.** Compléter sans supprimer, et prouver que **le diff ne contient que des ajouts** (`--compare`).      | Régénérer ferait monter les versions en douce — exactement ce qu'une phase « réparer sans rien changer d'autre » interdit.                                       |
| **Un renommage de workspaces avec `node_modules` chaud corrompt le lock.** Imposer `rm -rf node_modules` avant tout renommage.          | Cause racine datée : `531106c` (`@latelier/*` → `@kinetiq/*`, `apps/cv` → `apps/profile`), lock −6 829/+2 716, plateformes passées de linux=85/win32=26 à **0**. |
| **Un déploiement ne doit jamais être le chemin par défaut d'un push.** Gate explicite dès le jour 1.                                    | Le README promettait un déploiement automatique sur `main` qui n'a jamais fonctionné, sans garde ni protection de branche.                                       |

### 🟦 Générique — acquis pendant l'exécution du lot

| Leçon                                                                                                                                                                                                                                        | Pourquoi                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **npm ne sait pas réparer son propre lock amputé.** `npm install`, `--package-lock-only` et `--os/--cpu` forcés plafonnent tous au même point : npm ne revisite jamais un parent déjà résolu.                                                | Quatre stratégies mesurées, trois rejetées. Le standard doit documenter la bonne (injection additive + fermeture par npm) plutôt que de laisser chacun redécouvrir l'impasse.                        |
| **Écrire la garde AVANT la réparation, et la valider sur des cas connus.** Ici : lock sain → 0 absente, lock cassé → 172 ; puis 5 cas synthétiques pour le mode `--compare`.                                                                 | Sans cela, la garde aurait été juge et partie. Les cas synthétiques ont d'ailleurs révélé une erreur **dans mon harnais de test** (code de sortie masqué par un `\| sed`), pas dans le script.       |
| **Un critère strict est utile précisément quand il élimine la solution de repli.** Le repli prévu au plan (repartir du dernier lock sain) donnait un lock complet mais **65 montées de version** — invisible sans le critère.                | C'est le critère durci en cours de route qui l'a attrapé. Le standard doit poser le critère **avant** de connaître la difficulté.                                                                    |
| **La meilleure preuve de non-régression est un artefact identique, pas une suite de tests verte.** Build issu du lock réparé = **identique octet pour octet** à la production archivée.                                                      | Les 7 tests portaient tous sur le validateur du contrat : ils seraient restés verts même si le build avait changé. L'empreinte, elle, ne ment pas.                                                   |
| **Ne jamais reconstruire à la main ce qu'un gestionnaire de paquets déduplique.** L'injection est sûre pour des versions **exactes** ; la fermeture transitive (imbrications `vite/node_modules/@emnapi/runtime@1.11.1`…) doit rester à npm. | Première tentative : injection seule → `npm ci` refuse (`Missing: @emnapi/runtime from lock file`). La frontière entre « reconstructible » et « à déléguer » est celle de l'ambiguïté de résolution. |
| **Changer de version majeure d'outil change le comportement, pas seulement les bugs corrigés.** npm 12 bloque 6 scripts d'installation par défaut et abandonne les peer deps optionnelles que npm 10 gardait.                                | À vérifier explicitement lors de tout épinglage : ici sans conséquence (build identique), mais découvert par hasard.                                                                                 |

### 🟥 Frictions rencontrées

| Friction                                                    | Détail                                                                                                                                                                                                                                                                                                                           | Remède                                                                                                                                                                                                                 |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **La méthode prévue au plan ne marchait pas**               | Le plan prescrivait `rm -rf node_modules` + `npm install`. Résultat : 95 optionnelles toujours absentes, dont les trois binaires Linux indispensables au build.                                                                                                                                                                  | Un plan doit distinguer **l'objectif vérifiable** (lock complet + additif) de **la recette supposée**. Le skill doit boucler sur l'objectif, pas sur la recette.                                                       |
| **`git diff --numstat` ment sur un gros fichier structuré** | Le diff annonce **2 649 suppressions** sur le lockfile alors que la réparation n'en contient aucune : `comm -23 <(sort avant) <(sort après)` renvoie **0 ligne perdue**, et les 407 clés communes gardent contenu, ordre des champs et ordre global. Artefacts d'alignement de hunks, dus à l'insertion de 182 blocs entrelacés. | ⚙️ Ne jamais juger l'additivité d'un lockfile sur `git diff` : le juge est la garde sémantique, doublée d'un `comm` sur les lignes triées. À écrire dans le standard, sinon un relecteur humain refusera une PR saine. |
| **Essais destructeurs sur le dépôt réel**                   | Les stratégies A et B ont modifié le lock du dépôt avant d'être jugées mauvaises ; il a fallu `git checkout --` pour revenir.                                                                                                                                                                                                    | ⚙️ Tester les stratégies en **bac à sable** (copie des manifestes + lock) et n'appliquer que la gagnante. C'est ce qui a été fait à partir de la stratégie D.                                                          |

### ⚙️ À automatiser

- `scripts/verifie-lockfile.mjs` en CI **et** en hook pre-push, dans ses deux modes.
- Étape CI `npm install -g npm@<version épinglée>` avant `npm ci`.
- `scripts/repare-lockfile.mjs` : réparation additive réutilisable — à verser au standard.
- Comparaison **build ↔ artefact de référence** par empreinte, comme test de non-régression de phase.

## Lot 2 — Typage du Worker

### 🟦 Générique — règles de CI, issues de la relecture du lot 1

Ces deux règles ont été relevées **après** la fusion du lot 1, en relisant le fichier CI qu'il
installait. Elles sont appliquées dans le lot 3 (cf. `docs/audit/suivi-phase-0.md`).

| Leçon                                                                                                                                                                                                                                                                             | Pourquoi                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Un déploiement manuel ne part que de `main`.** `workflow_dispatch` seul ne suffit pas : il faut `github.ref == 'refs/heads/main'` en plus de `github.event_name == 'workflow_dispatch'`.                                                                                        | Sans la seconde condition, n'importe quelle branche — y compris une branche de travail à moitié faite — peut être déployée en production depuis l'onglet Actions. La garde « un push ne déploie plus » était en place, la garde « une branche quelconque ne déploie pas » manquait.                                        |
| **Un push n'annule jamais un déploiement en cours.** `concurrency.cancel-in-progress` doit être conditionné : `${{ github.event_name == 'pull_request' }}`.                                                                                                                       | Annuler le run précédent est une économie sur une PR ; sur un déploiement, c'est une interruption au milieu d'un envoi vers la production. Le même `concurrency` servait les deux cas.                                                                                                                                     |
| **La vérification de types doit être indépendante des artefacts de construction.** Un `tsconfig` de vérification vise les **sources** par `paths` ; à défaut, le script de vérification construit lui-même ce dont il dépend.                                                     | Ici `apps/api` consommait le `dist/` du contrat : sur un dépôt fraîchement cloné — le cas de la CI, où `typecheck` précède `build` — la vérification échouait faute de types. Pire : des déclarations périmées masquent exactement l'erreur qu'on cherche (`ErreurApi` élargi dans la source, encore étroit dans `dist/`). |
| **Ne jamais toucher la configuration de construction pour faire plaisir à `tsc`.** Les objections de `tsc` qui ne portent que sur l'émission (TS6059 « not under rootDir ») se neutralisent dans un `tsconfig.typecheck.json` dédié, pas dans le fichier que lit le constructeur. | La vérification n'émet rien : l'objection est hors sujet. La corriger dans `tsconfig.app.json` aurait changé la disposition de sortie d'`ng build` — un changement de comportement interdit en phase de remise en état.                                                                                                    |
| **Un pas de génération de types qui a besoin du runtime n'est pas disponible partout.** Le vérifier **avant** de l'inscrire au plan.                                                                                                                                              | `npx wrangler types` lance workerd pour produire les types du runtime : impossible sur un poste que workerd refuse. Le repli — ne déclarer que ce que le code utilise vraiment — était ici sans coût, parce qu'aucun binding n'est lu dans le code.                                                                        |
| **Pour un Worker, retirer `DOM` de `lib` fait partie du typage.** Hériter de la configuration des applications web laisse passer du code impossible en production.                                                                                                                | `tsconfig.base.json` inclut `DOM` pour Angular. Sans `lib: ["ES2022"]`, `document.title` compile dans le Worker — et casse à l'exécution.                                                                                                                                                                                  |
| **Prouver « aucun changement visible » sur un service, c'est comparer ses réponses, pas seulement relire le diff.**                                                                                                                                                               | Le typage de la réponse 404 ne change rien par construction — mais c'est le genre d'affirmation qu'on vérifie : `dist/` identique à l'archive **et** corps de `/api/profile` et `/api/inconnu` comparés octet pour octet à la production relevée au lot 0.                                                                 |

### 🟥 Frictions rencontrées

| Friction                                                            | Détail                                                                                                                                                                                                                                                                            | Remède                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`npm install --package-lock-only` défait la réparation du lot 1** | Ajouter une dépendance d'espace de travail par cette commande a **supprimé** l'entrée `@angular/animations` (peer optionnelle que npm 12 ne retient plus, réinjectée à la main au lot 1) et resynchronisé `engines` au passage : 3 ajouts, 19 suppressions pour une ligne voulue. | Sur un lock réparé à la main, toute addition reste **chirurgicale** (éditer l'entrée de l'espace de travail concerné), puis repasser la garde dans ses deux modes. ⚙️ La garde `--compare` doit faire partie du réflexe « j'ai touché au lock », pas seulement de la réparation. |
| **Trois erreurs `tsc` qui n'en sont pas**                           | `tsc -p apps/profile/tsconfig.app.json --noEmit` sort 3 erreurs TS6059, toutes sur la disposition des fichiers émis. Lues trop vite, elles passent pour « beaucoup d'erreurs de types » et déclenchent l'arrêt prévu au plan.                                                     | Trier les erreurs par code avant de juger du volume : une erreur de configuration et une erreur de type ne se traitent pas pareil, et ne mesurent pas le même risque.                                                                                                            |

### ⚙️ À automatiser

- `npm run typecheck` en hook pre-push, à côté de `verify:lockfile`.
- Comparaison des réponses de l'API **avant / après** (corps + en-têtes) comme test de non-régression de lot, à partir de la photo d'avant.

### 🟨 Propre à ns-studio

- `apps/api/worker-configuration.d.ts` **n'est pas produit sur ce poste** : `wrangler types` exige workerd (macOS 13.5+). Le Worker ne lit aucun binding, donc rien ne manque aujourd'hui ; le jour où il lira `env`, il faudra générer ce fichier sur Linux (ou en CI) ou adopter `@cloudflare/workers-types`.
- La vérification de types ne couvre pas les gabarits Angular (`strictTemplates`) : c'est `ng build`, donc l'étape `build`, qui les contrôle.

## Lot 3 — Garde de déploiement, documentation fidèle, licence

### 🟦 Générique — à verser au standard

| Leçon                                                                                                                                                                                        | Pourquoi                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L'état du travail vit dans le dépôt, pas dans la mémoire d'une session.** Un fichier de suivi par phase et un journal des leçons, lus **en premier** à chaque session, avant toute action. | Une nouvelle session a repris le lot 2 en cours — sans contexte conversationnel — et n'a rien perdu : le lot en cours, les mesures, le blocage et ses trois tentatives, les décisions déjà prises étaient tous dans `docs/`. C'est ce qui a marché, donc c'est ce qui devient une règle : la session est jetable, le dépôt ne l'est pas. → inscrit en `CLAUDE.md` §1. |
| **Une documentation fausse est une dette, pas un détail** : elle fait prendre des décisions sur un dispositif qui n'existe pas.                                                              | Le README promettait un déploiement automatique sur `main` — qui n'a jamais fonctionné — et « la CI passe ce test avant tout déploiement », faux par les deux chemins. Quelqu'un qui pousse sur `main` en croyant le site mis à jour ne vérifie pas la production.                                                                                                    |
| **Une affirmation de documentation se vérifie comme du code.** Trois classes de verdict : vraie, fausse, ou _rendue vraie par ce lot_.                                                       | Ici : une corrigée (déploiement), une **rendue vraie** (`needs: ci` + la chaîne de `npm run deploy`), une remplacée par la limite réelle et son contournement (l'impression). Les trois ne se traitent pas pareil — et la deuxième n'est honnête qu'une fois le code en place.                                                                                        |
| **Ce qu'on n'a pas observé se dit.** Une limite établie **par lecture du code** s'écrit comme telle, avec ce qui a été lu ; elle ne s'écrit pas comme un constat.                            | La troncature à l'impression est déduite de `min-block-size: 100dvh` sur l'iframe et de l'absence de toute règle `@media print` la ciblant (`grep` sur quatre dossiers). Le PDF n'a pas été produit : l'impression n'est pas observable depuis ce poste. La formulation doit porter cette différence, sinon la prochaine session la croira mesurée.                   |
| **La commande de déploiement locale rejoue les gardes de la CI.** `deploy` = vérifications → build → envoi, jamais un alias de l'outil d'envoi.                                              | Sinon il existe deux chemins vers la production, dont un sans garde — et c'est toujours celui-là qu'on prend quand on est pressé. Corollaire : l'affirmation « rien ne part sans être testé » devient vraie des deux côtés, pas seulement sur le papier.                                                                                                              |
| **Un dépôt public sans `LICENSE` est « tous droits réservés ».** La licence fait partie de la mise en état, pas de la finition.                                                              | Le dépôt était public depuis le début, sans licence ni champ `license` : personne ne pouvait légalement le réutiliser, alors que c'était l'intention.                                                                                                                                                                                                                 |
| **Un champ de données qui ressemble à une exception doit porter sa justification dans le code, avec l'ordre de ne pas le retirer.**                                                          | `permis` ressemble aux champs écartés par la doctrine « pas de données personnelles » (adresse, téléphone, naissance). Justifié dans le README seulement, il aurait été supprimé à la première relecture de la doctrine. Le commentaire du contrat dit maintenant pourquoi il reste et interdit l'analogie.                                                           |
| **Quand un document de référence devient faux, on le corrige — même s'il est surchargé ailleurs.**                                                                                           | `AGENTS.md` décrivait encore l'ancien `npm run deploy` et un style de commit abandonné. Le laisser faux en comptant sur `CLAUDE.md` pour le contredire, c'est garantir qu'un lecteur (ou un agent) tombera sur la mauvaise moitié.                                                                                                                                    |
| **Une garde exprimée dans la plateforme de CI n'est pas vérifiable localement : le dire, et dire quand elle sera éprouvée.**                                                                 | `github.ref == 'refs/heads/main'` et `cancel-in-progress: ${{ … }}` ne sont évalués que par GitHub. La CI de la PR prouve la validité du fichier, pas le comportement de la garde — qui ne sera constaté qu'au premier déclenchement manuel. Ce qui est vérifiable localement : que le YAML parse (Prettier le fait).                                                 |
| **Un relevé qui échoue trois fois pour la même cause hors de portée n'est pas « à réessayer » : il est à replacer au moment où il est indispensable.**                                       | Le relevé Cloudflare a été retenté à chaque lot, avec le même résultat et le même coût. Déplacé en étape 0 du déploiement manuel, il est non seulement faisable (session renouvelée par l'utilisateur) mais **juste** : l'identifiant doit désigner la version que le déploiement va remplacer. Relevé trop tôt, il est périmé ; relevé après, il est inutile.        |

### 🟥 Frictions rencontrées

| Friction                                                                  | Détail                                                                                                                                                                                                                                   | Remède                                                                                                                                                                                                         |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Un blocage dépendant de l'utilisateur relancé à chaque lot**            | Trois tentatives de relevé wrangler, trois fois le même message, pour une session que seul l'utilisateur peut renouveler. Chaque tentative a coûté une section de suivi et une relance dans la conversation, sans information nouvelle.  | Un blocage non résoluble par l'agent se consigne **une fois**, puis se **planifie** à l'étape où il est nécessaire. ⚙️ Le skill doit tenir une liste « à faire par l'humain, à telle étape », pas re-tenter.   |
| **Un champ de `package.json` qu'on ne peut pas ajouter « normalement »**  | Ajouter `"license"` est trivial, mais `npm` ne resynchronise pas l'entrée racine du lock sans supprimer `@angular/animations`. Il a fallu vérifier que `npm ci` et la garde ignorent bien `license` avant de conclure « ne rien faire ». | Sur un lock réparé à la main, la question n'est pas « quelle commande » mais « ce champ est-il contrôlé à l'installation ? ». Si non : ne pas toucher au lock, et **écrire pourquoi**.                         |
| **Inexactitudes supplémentaires découvertes en relisant, hors périmètre** | Le plan listait 3 affirmations fausses ; la relecture en a trouvé 2 autres (l'arborescence décrivant la CI, et « `apps/api` n'a pas de `tsc` » — faux depuis le lot 2) et 3 commandes absentes du tableau.                               | ⚙️ Un lot « documentation fidèle » doit relire **le fichier entier**, pas seulement les lignes citées au plan. Et toute PR qui change un script ou une étape de CI devrait vérifier les docs qui la décrivent. |

### ⚙️ À automatiser

- **Garde de cohérence doc ↔ dépôt** : vérifier que chaque commande citée dans `README.md`/`AGENTS.md`
  existe dans `package.json`, et que chaque script de `package.json` est documenté. Un lot « doc fidèle »
  ne devrait pas être nécessaire une deuxième fois.
- Vérifier la présence de `LICENSE` + `package.json#license` dans la checklist « sous-projet conforme ».
- Vérifier que la commande `deploy` contient bien les gardes, et pas seulement l'outil d'envoi.

### 🟨 Propre à ns-studio

- L'impression depuis la shell est **tronquée** : l'iframe de `remote-frame` est plafonnée à `100dvh` et
  aucune règle `@media print` ne la libère. Contournement : imprimer `/remotes/profile/`. Correction en
  Phase 1 (règles d'impression sur `.remote`, ou redirection de l'impression vers le document encadré).
- `wrangler deploy --dry-run` annonce 10 fichiers d'assets pour 8 sur le disque. Non expliqué, sans
  conséquence (le dossier est byte-identique à l'archive du lot 0). **Clos au lot 4** : wrangler
  compte les sous-dossiers avec les fichiers (11 pour 9 fichiers + 2 sous-dossiers).

## Lot 4 — En-têtes de sécurité

### 🟦 Générique — à verser au standard

| Leçon                                                                                                                                                                                                                                           | Pourquoi                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Une politique déclarée deux fois doit être vérifiée par un test, pas par une convention de relecture.** Sur Cloudflare Workers, `_headers` ne couvre pas les réponses du code : deux mécanismes, donc deux déclarations de la même politique. | Les deux ne divergent pas le jour où on les écrit — elles divergent au troisième lot, quand quelqu'un ajoute un en-tête d'un seul côté. Un `curl -I` ne le dirait qu'après un déploiement. Un test qui lit le fichier de configuration et interroge le code en mémoire le dit en CI, pour vingt lignes.                                                                                                                                      |
| **`Report-Only` ne protège de rien : si un lot « pose des en-têtes de sécurité » et que tout part en Report-Only, il a livré de la mesure, pas de la protection.** Toujours accompagner une CSP Report-Only d'au moins un en-tête appliqué.     | Le plan prévoyait `frame-ancestors 'self'` comme protection contre le cadrage. En Report-Only, cette directive **signale** et n'interdit rien : sans `X-Frame-Options: SAMEORIGIN`, le lot aurait atteint zéro de son objectif annoncé tout en paraissant complet. Distinguer, dans tout lot de sécurité, ce qui mesure de ce qui applique.                                                                                                  |
| **`Strict-Transport-Security` se traite à part : c'est le seul en-tête dont l'effet survive à son retrait.** Il ne se pose pas avant que le nom de domaine définitif soit arrêté.                                                               | Les autres en-têtes se retirent en redéployant. HSTS est mémorisé par le navigateur — 180 jours avec le défaut de Hono : une erreur engage une adresse qu'on ne peut pas reprendre, y compris pour les visiteurs déjà venus. Le poser est une décision de nom de domaine, pas de configuration.                                                                                                                                              |
| **Les défauts d'un middleware de sécurité s'inventorient dans un test.** Figer la liste exacte des en-têtes envoyés, pas seulement ceux qu'on a demandés.                                                                                       | `secureHeaders()` de Hono pose **douze** en-têtes par défaut, dont sept non déclarés côté assets. Non inventoriés, ils produisent deux effets : une asymétrie pages/API que personne n'a décidée, et une montée de version qui change la politique de production en silence. Le test les nomme : l'asymétrie devient un point ouvert documenté, et une montée de version échoue en CI.                                                       |
| **Un critère de non-régression doit nommer le nombre de fichiers attendu, pas « identique ».** Ici : « 8/8 fichiers identiques, `index.html` compris, `_headers` en seul ajout ».                                                               | « Le build ne change pas » est invérifiable quand le lot **ajoute** un fichier à la sortie. Un critère chiffré avec la liste de l'écart autorisé se vérifie en une commande (`diff` de deux listes d'empreintes) et ne laisse aucune place à l'interprétation. C'est le critère que l'utilisateur a précisé à l'ouverture du lot — il a tenu exactement.                                                                                     |
| **Activer un dossier d'assets, c'est ouvrir un chemin vers la production : vérifier qu'il est vide, puis le garder vide par un test.**                                                                                                          | `"assets": [{ "glob": "**/*", "input": "public" }]` copie tout. Le plan prévoyait un `ls -aR` avant d'activer _(ajustement 5a)_ — une vérification à un instant, qui ne protège pas le lot suivant. Transformée en test (« `public/` ne contient que `_headers` »), elle protège aussi ceux d'après, et pour le même prix.                                                                                                                   |
| **Un fichier de configuration qui part dans la sortie du build doit être vérifié non servi — et le critère est le corps de la réponse, pas son code HTTP.**                                                                                     | `_headers` atterrit à la racine des assets, à côté d'`index.html` : si la plateforme le servait, la politique de sécurité serait publique. Le plan attendait un **404** _(ajustement 5b)_. Mais avec un repli SPA (`not_found_handling`), un chemin exclu du manifeste rend `index.html` en **200** — et un critère écrit en termes de code HTTP aurait affiché un faux échec. « Le fichier n'est pas servi » se vérifie en lisant le corps. |
| **Un test qui importe le code serveur a besoin de ses dépendances construites : le script de test les construit, comme celui de vérification de types.**                                                                                        | `npm test` ne construisait que le contrat par ses sources relatives. Le test des en-têtes importe le Worker, donc `@ns-studio/profile-contract` par son `dist/` — absent d'un dépôt fraîchement cloné, et la CI lance `test` **avant** `build`. Un `npm run build:contract &&` en tête du script, exactement comme `typecheck` le fait déjà.                                                                                                 |
| **Une observation « non expliquée, non bloquante » se clôt au lot suivant par un second point de mesure, pas par une lecture de code.**                                                                                                         | `wrangler deploy --dry-run` annonçait 10 assets pour 8 fichiers. Le lot 4 en a ajouté un : 11 pour 9. L'écart constant de +2 = le nombre de sous-dossiers. Deux mesures suffisent à clore une observation de ce rang — et l'inférence se dit comme telle, pas comme une lecture du code de wrangler.                                                                                                                                         |

### 🟥 Frictions rencontrées

| Friction                                                                                                       | Détail                                                                                                                                                                                                                                                                      | Remède                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Le plan a sous-estimé un en-tête, et c'était celui qui portait l'objectif**                                  | Le plan listait `frame-ancestors 'self'` dans « en-têtes posés » **et** la CSP en Report-Only, deux lignes plus bas. Les deux ensemble veulent dire « aucune protection contre le cadrage » — mais la contradiction ne saute aux yeux qu'en rédigeant le test.              | ⚙️ Dans un lot de sécurité, dresser le tableau **en-tête × mode (appliqué / signalé)** avant d'écrire le premier fichier. Une ligne « signalé » qui porte un objectif du lot est un défaut de plan, pas un détail d'implémentation. |
| **Les valeurs de deux déclarations doivent être égales à la chaîne près, et rien ne le garantit à l'écriture** | Hono construit la CSP depuis un objet (ordre des clés, `camelCase` → `kebab-case`, jointure `; `) ; `_headers` la porte en texte. Il a fallu lire le code du middleware pour savoir quelle chaîne il produirait, puis ordonner les clés de l'objet pour la faire coïncider. | ⚙️ Écrire le test de parité **avant** les deux déclarations : il donne la chaîne cible et transforme un alignement à l'œil en échec reproductible.                                                                                  |

### ⚙️ À automatiser

- **Garde « politique déclarée deux fois »** : réutilisable sur tout Worker servant des assets — lire `_headers`, interroger l'application en mémoire, comparer en-tête par en-tête. C'est vingt lignes et ça remplace un `curl -I` post-déploiement.
- **Garde « dossier d'assets vide »** : tout dossier copié intégralement dans la sortie du build (`public/`, `static/`…) a une liste de fichiers attendue, et cette liste est un test.
- **Checklist « en-têtes » du standard** : les deux mécanismes · la CSP en Report-Only d'abord, avec un en-tête appliqué pour le cadrage · HSTS reporté au nom de domaine définitif · le 404 sur le fichier de configuration · l'inventaire des défauts du middleware.
- **Critère de non-régression chiffré** : la comparaison « liste d'empreintes de la sortie ↔ artefact de référence » est mécanique. Elle devient une étape de CI le jour où l'artefact de référence est attaché à une release _(cf. « Où vit l'artefact de référence d'une release ? »)_.

### 🟨 Propre à ns-studio

- La CSP ne peut pas passer en mode appliqué tant que les styles de composant Angular sont injectés en `<style>` : `style-src` exige `'unsafe-inline'`. Levée possible par nonce ou extraction des styles — Phase 1.
- `img-src` doit accepter `data:` : le favicon est une icône SVG en ligne dans `apps/web/src/index.html`. Pas un contournement, un choix assumé (« pas de requête supplémentaire, pas de 404 sur `/favicon.ico` »).
- Sept en-têtes de Hono ne couvrent que `/api/*`. Les étendre aux pages demande d'observer `Cross-Origin-Opener-Policy` et `Origin-Agent-Cluster` sur un document **et son iframe** — donc après déploiement. Point ouvert de Phase 1, inventorié par un test en attendant.
- `wrangler deploy --dry-run` compte les sous-dossiers avec les fichiers (11 annoncés pour 9 fichiers + 2 sous-dossiers). L'observation du lot 3 est close.

| **a. Génère-t-on les types workerd en CI Linux, et isole-t-on `dev-node.ts` dans sa propre configuration de types ?**                                                    | `wrangler types` exige workerd, qui refuse macOS 12.6 : `apps/api/worker-configuration.d.ts` n'existe pas (lot 2). Sans conséquence tant que le Worker ne lit aucun binding — mais le jour où il lira `env`, il faut une source de types.
